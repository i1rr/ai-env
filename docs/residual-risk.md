# Residual risk

`ai-env` reduces the blast radius of an autonomous AI coding agent. It does
not make autonomous agents perfectly safe. This document is the honest list
of risks the tool acknowledges but does not currently close, organised by
where the risk lives.

Read this together with [`threat-model.md`](threat-model.md) (the actors and
attack surfaces the tool is designed against) and
[`enforcement-boundaries.md`](enforcement-boundaries.md) (which control
actually enforces which boundary).

## What the tool will and will not promise

`ai-env` will promise:

> Default mode avoids mounting host secrets, avoids the host Docker socket,
> avoids direct active-workspace writes, blocks RFC1918 + cloud metadata +
> loopback egress, denies outbound traffic by default, brokers GitHub
> writes, and exports reviewable patches.

`ai-env` will **not** promise:

- No sandbox escape is possible.
- No prompt injection can succeed.
- No malicious dependency can ever exfiltrate data.
- No unsafe PR can ever be opened.
- Every shell command an agent issues will be intercepted.
- Raw provider tokens, if explicitly injected, will stay confidential.

If your workflow requires any of those promises, `ai-env` is not the right
tool by itself; pair it with code review, branch protection, vault rotation,
and CI-side validation.

## Residual risk under the primary backend

Even with the primary `docker_sbx` backend, microVM isolation, network
deny-by-default, and the brokered PR path, the following remain unaddressed
in v0.1.

### 1. Backend / hypervisor bugs

The `docker_sbx` adapter delegates to a Docker-Sandboxes-compatible runtime.
A vulnerability in the runtime, the hypervisor, or the host kernel can let
a sufficiently sophisticated agent escape the sandbox. `ai-env` does not
add a second isolation layer below the backend; the backend is the boundary.

Mitigation guidance: keep the runtime patched, prefer microVM-backed
backends over container-only ones, and treat the workstation as if a
high-privilege process were running on it.

### 2. Backend CLI surface changes

The `sbx` CLI flags and JSON output formats may change between runtime
versions. `internal/backend/docker_sbx/compat.go` pins known-compatible
versions; an unknown version fails closed. A regression in a *known*
version that silently relaxes isolation will not be caught by version
pinning alone.

Mitigation guidance: monitor backend release notes, re-run the
`tests/acceptance/` suite after backend upgrades, and run with
`AI_ENV_BACKEND_INTEGRATION=1` in CI.

### 3. Malicious dependency inside the sandbox

`npm install` / `pip install` / `go mod download` runs arbitrary code.
`ai-env` defaults to `--ignore-scripts` where the package manager honors it,
but a malicious package can still execute code at import time (Python),
postinstall (npm with scripts enabled), or build (Go cgo). Once that code
runs:

- It cannot read host secrets (not mounted).
- It cannot reach the host network (allowlist + always-blocked CIDRs).
- It **can** read the workspace contents and try to exfiltrate via any
  allowed egress destination.

Mitigation guidance: keep the allowlist tight; review the diff for
unexpected new dependencies; rerun `ai-env scan` after dependency updates.

### 4. Exfiltration through allowed destinations

The allowlist is host-level, not request-level. A malicious agent that can
reach `github.com` (allowed for the broker push) can also attempt to push
data to attacker-controlled gists, issues, or repositories under that host.
HTTP method enforcement is only applied to brokered API calls; arbitrary
HTTPS traffic to allowed hosts is not method-filtered in v0.1.

Mitigation guidance: scope `allow_domains` to the minimum the agent needs;
prefer brokered paths over raw allowlist entries; review network-events
post-run.

### 5. Prompt injection inside the sandbox

Repository content (`README.md`, comments, generated files, test fixtures)
can carry instructions the agent acts on. `ai-env` cannot stop the agent
from being influenced; it only stops the influenced agent from doing
externally-visible damage. A prompt-injected agent that decides to rewrite
the test suite to silently pass will not be caught by the network policy,
the broker, or the scanner.

Mitigation guidance: the export gate and human code review are the
boundary against this class of attack. Do not skip the diff review.

### 6. Continuing from a compromised run

`ai-env run --continue` reuses the workspace and feeds a sanitized summary
of the previous run into the next prompt. The summary is generated by the
supervisor, not by the agent, so a malicious agent cannot inject arbitrary
text into it directly. The workspace itself, however, can carry
instructions the next agent reads (modified `README`, planted test files,
poisoned comments).

`--continue` after a quarantined run is blocked by default; the operator
must pass `--allow-continue-after-quarantine` to override.

Mitigation guidance: review the diff before continuing; do not continue
from a quarantined run unless you intend to investigate it.

### 7. Misconfigured allowlist

`policy.yaml` is operator-edited. A wide allowlist (`*.s3.amazonaws.com`),
a wildcard `allow_domains`, or an accidentally permissive `commands.default`
silently opens exfil paths. The engine does not validate allowlist entries
against a curated "known-safe" list; it accepts what the operator wrote.

Mitigation guidance: prefer the default `policy.yaml`
(`ai-env policy init`); review changes via `ai-env policy check`; commit
`policy.yaml` so changes show up in code review.

### 8. Provider token theft from the host

The provider proxy holds the Anthropic / OpenAI API key in host process
memory. A separate process running as the same OS user can read that
memory, the loopback port, or the proxy log file. `ai-env` does not isolate
the proxy from co-tenant processes on the host.

Mitigation guidance: do not run `ai-env` on a multi-tenant host; rotate
provider keys regularly; prefer backend-managed credentials over raw token
injection.

### 9. Brokered PR with deceptive contents

The broker scans PR title, body, branch name, and commit messages for
secrets, and it enforces branch prefix + protected branch + path gate
checks. It does not inspect the **content** of the PR diff beyond the
hard-blocker matrix (high-confidence secret findings, `.ai-env/`,
`.github/workflows/**` under `ModePR`). A PR that subtly breaks production
code without touching workflows, lockfiles, or `.ai-env/` will be opened
once the gate clears.

Mitigation guidance: the draft PR + human review is the boundary; never
auto-merge `ai-env`-opened PRs.

### 10. Protected paths the agent legitimately needs to change

`.github/workflows/**`, `migrations/**`, `terraform/**`, and lockfiles are
all flagged as protected. An agent given a task that legitimately requires
changing those paths will be blocked from PR export and will produce a
patch the operator must apply manually.

Mitigation guidance: this is the intended behaviour. Move the protected
edit through manual review.

### 11. Operator opts into unsafe modes

The following flags relax the threat model on purpose:

- `--accept-reduced-isolation`: enables the rootless docker / podman
  fallback. Shares host kernel. Documented in
  [`enforcement-boundaries.md`](enforcement-boundaries.md).
- `--unsafe-host-network`: lets the fallback backend reach the host network.
  Defeats the egress policy.
- Raw provider token injection (`raw_env_explicit` credential mode):
  exposes the provider token to every process inside the sandbox.

A run that uses any of those modes records the choice in `run.json` and
prints the reduced-safety banner. The threat model assumes the operator
who passed the flag understood what they gave up.

### 12. Race between scan and export

`ai-env scan` writes `secret-scan.json` into the run directory; `ai-env
patch` / `ai-env pr` reads it back. Between those two commands the
operator (or a hostile process running as the same OS user) can modify the
scan file or the workspace. The CLI does not seal the run directory.

Mitigation guidance: run `scan` and `patch` / `pr` in the same shell
session; do not edit `.ai-env/` between them.

## Residual risk under the reduced-isolation fallback

The rootless `docker` / `podman` backends are documented as **not
equivalent** to the primary microVM backend. They share the host kernel.
A kernel or container runtime exploit can compromise the host directly.

The verbatim warning the adapter prints is:

```text
This backend provides reduced isolation. It is suitable for development
and testing, but not for high-risk autonomous execution with untrusted
dependencies or secrets.
```

Use the fallback for:

- Local development and CI for `ai-env` itself.
- Testing the CLI surface without a Docker Sandboxes-capable runtime.

Do not use the fallback for:

- Untrusted dependencies you have not seen before.
- Autonomous runs with real production-adjacent credentials.
- Multi-tenant workstations.

## Risks the tool deliberately does not address

The following are out of scope for v0.1 and are unlikely to be in scope for
v0.2 either.

### Side-channel attacks across the sandbox

Timing, cache, microarchitectural, power, and acoustic side channels are
not modelled. An attacker with side-channel capability on the host has
already won.

### Host compromise outside the env

If the developer workstation is already compromised (rootkit, malicious
browser extension reading clipboard, another user's process running as the
operator), `ai-env` cannot help. Every control in the tool assumes the
host's user account is honest.

### Supply-chain attacks against `ai-env` itself

A compromised `ai-env` binary defeats every control. The release pipeline
signs binaries and emits an SBOM; verifying signatures and pinning the
binary version is the operator's responsibility. There is no runtime
integrity check inside `ai-env` for `ai-env`.

### Compromise of the model provider

If Anthropic or OpenAI is compromised and serves malicious completions,
the agent will execute them inside the sandbox. The sandbox blast radius
applies, but the operator's task and prompt have already reached the
attacker.

### Adversarial cooperation among agent processes

Multi-agent workflows where two agents in two sandboxes coordinate to
exfiltrate are not modelled. Each sandbox enforces its own controls;
cross-sandbox coordination through allowed channels (a shared repository,
a shared package registry) is not detected.

### MCP server compromise

MCP gateway enforcement is deferred to v0.2 / v0.3. v0.1 does not interpose
on MCP tool calls. If an MCP server the agent connects to is malicious, it
can influence the agent within the bounds of the agent's other constraints
(network policy still applies to outbound HTTP from MCP-issued tools).

### Native Windows

Native Windows is out of scope. WSL2 may work but is not a supported
target. The threat model assumes Linux or macOS as the host.

## Summary checklist for operators

Before relying on `ai-env` for a given run:

1. Am I using the primary backend, or did I pass
   `--accept-reduced-isolation`? If the latter, am I OK with kernel-shared
   isolation?
2. Is `policy.yaml`'s `allow_domains` the minimum the agent needs?
3. Did I pass `--unsafe-host-network` or any other unsafe flag? Is that
   recorded in `run.json`?
4. Did I review the diff (`ai-env diff`) before exporting?
5. Did `ai-env scan` produce only entropy warnings, or did it flag a
   high-confidence finding?
6. Is the brokered PR going to a non-protected branch with the
   `ai-env/` prefix?
7. Are the provider tokens I gave the host machine ones I am OK rotating?

If any of those answers makes you uncomfortable, the threat model is asking
you to stop and address it before proceeding.
